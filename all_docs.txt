## what system design applied in this SmartRecruit project?

Yes. For the **SmartRecruit system I documented**, the design is primarily a **microservices-based distributed system**, with several supporting architectural patterns.

### **Main system-design patterns applied**


| **System design**                       | **How it is applied in SmartRecruit**                                                                                                        |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Microservices Architecture**          | 9 independent business services: Auth/User, Business, Job, Application, CV/AI, Subscription, Interview, Notification, Analytics              |
| **Database-per-Service**                | Each service owns its PostgreSQL database/schema and data. Services do not directly access another service's DB.                             |
| **API Gateway**                         | Spring Cloud Gateway provides a single entry point for the React frontend and routes requests to backend services.                           |
| **Kubernetes-Native Service Discovery** | Kubernetes Services/DNS provide service discovery instead of Eureka.                                                                         |
| **Event-Driven Architecture**           | Apache Kafka is used for asynchronous communication and domain events between services.                                                      |
| **Synchronous REST Communication**      | REST APIs are used when an immediate response is required.                                                                                   |
| **Transactional Outbox Pattern**        | Recommended for reliably publishing database changes as Kafka events without losing events.                                                  |
| **Idempotent Consumers**                | Kafka consumers should safely process the same event more than once.                                                                         |
| **Saga / Process Manager**              | Used conceptually for multi-service business workflows such as subscriptions, applications, interviews, etc.                                 |
| **CQRS / Read Models**                  | Particularly useful for the Analytics service, where reporting data can be built from events rather than querying other services' databases. |
| **Circuit Breaker + Retry**             | Selective protection for critical synchronous service-to-service calls.                                                                      |
| **Resource/Tenant Authorization**       | Services verify that a recruiter actually owns or is authorized to access a business, job, application, etc.                                 |
| **Object Storage**                      | CVs and employment-proof documents are stored as files in S3-compatible object storage; PostgreSQL stores metadata.                          |
| **Caching**                             | use Redis as performance layer for selective caching layer for read-heavy and frequently accessed data.                                      |
| **External AI Adapter**                 | The CV/AI service isolates the external AI provider from the rest of the system.                                                             |
| **Mock Payment Adapter**                | Payment integration is abstracted so the project can start with a mock provider and later replace it.                                        |
| **Containerization**                    | Each service is packaged as a Docker image.                                                                                                  |
| **Orchestration**                       | Kubernetes is the production deployment target.                                                                                              |
| **Observability**                       | Spring Boot Actuator, Micrometer, metrics, structured logs and distributed tracing foundations are included.                                 |


### **Overall architecture**

The important distinction is that **Microservices Architecture is the main system design**, while the others support it:

```
                         React + TypeScript
                                │
                                ▼
                       ┌─────────────────┐
                       │   API Gateway   │
                       └────────┬────────┘
                                │
       ┌────────────────────────┼────────────────────────┐
       │            │            │            │            │
       ▼            ▼            ▼            ▼            ▼
    Auth/User    Business       Job      Application    CV/AI
       │            │            │            │            │
       └────────────┴────────────┴────────────┴────────────┘
                                │
                         Apache Kafka
                                │
       ┌────────────────────────┼───────────────────────┐
       ▼                        ▼                       ▼
 Subscription              Interview             Notification
       │                        │                       │
       └────────────────────────┼───────────────────────┘
                                ▼
                           Analytics
```

And underneath:

```
Each service
     │
     ├── REST API
     ├── Business logic
     ├── Own PostgreSQL DB
     └── Kafka producer/consumer
```

For files:

```
CV/AI Service
     │
     ├──────────────► PostgreSQL
     │                metadata
     │
     └──────────────► S3-compatible Object Storage
                      actual CV / documents
```

### **The most important design principle**

The architecture follows:

> **Each microservice owns its business capability and its data.**

For example, the Application Service **does not directly query the Job Service's PostgreSQL database**.

Instead:

```
Application Service
       │
       │ REST / Kafka
       ▼
   Job Service
       │
       ▼
 Job Service DB
```

# SmartRecruit Actors and Access Model

## 1. Actors

SmartRecruit exposes exactly **four application actors** in the use-case model:

| Actor | Description | Main responsibilities |
|---|---|---|
| **Anonymous User** | Unauthenticated visitor | Browse the public job timeline, search/filter offers, view public offer details, start the application flow |
| **Candidate** | Authenticated job seeker | Manage profile/CVs, apply to jobs, receive AI recommendations/ATS analysis, manage subscriptions, interviews and notifications |
| **Recruiter** | Authenticated company-side user approved by the platform | Manage authorized company information, job offers, applications, candidate hiring status, interviews, analytics and recruiter subscription |
| **Platform Administrator** | Platform management user | Manage users, recruiter approval, businesses, subscription plans/company subscriptions and platform administration |

External AI, MinIO, Kafka, email providers, webhook destinations and payment implementations are **system integrations/components, not actors** in the business use-case diagram.

## 2. Anonymous User

- View the public LinkedIn-style job timeline.
- Search and filter job offers.
- View public job-offer details.
- Start an application.
- When applying, authentication is required and the user is redirected to sign up/sign in.

## 3. Candidate

### Account and profile
- Register and sign in.
- Candidate accounts are automatically activated after registration.
- View and update permitted profile information.

### CV and AI
- Upload CVs.
- Delete CVs.
- Manage CV versions according to subscription limits.
- Request ATS analysis.
- Receive AI-suggested jobs and CV-related recommendations.

CV files are stored in MinIO/S3-compatible object storage; PostgreSQL stores metadata and analysis references.

### Jobs and applications
- Browse/search offers without authentication.
- Apply after authentication.
- View personal applications and statuses.

### Subscription
- View plans.
- Subscribe, upgrade, downgrade, renew and cancel according to plan rules.
- View billing/subscription history.

### Interviews
- View personal interviews and calendar.
- Open the external meeting link supplied by the recruiter.
- Cancel an interview where permitted.
- Request a delay with a proposed date/time.

### Notifications
- View notifications.
- Mark notifications read/unread.
- Delete own notifications.

## 4. Recruiter

### Registration and approval
- Register with required recruiter information.
- Upload employment proof during registration.
- Remain pending until Platform Administrator approval.
- Sign in only after approval.

### Business and recruitment
- Manage only authorized company information.
- Create, update, close, reopen and delete job offers according to authorization/subscription rules.
- View and manage applications belonging to authorized company offers.
- Update candidate application status.

### Interviews
- Schedule, reschedule and cancel interviews.
- Enter an external meeting URL, such as a Zoom or Google Meet link, for the candidate.
- Mark interviews as done.
- Accept/reject candidate delay requests.

The Interview Service does **not** host the video session. It stores and exposes the external meeting link.

### Dashboard and subscription
- View recruitment analytics and export PDF reports.
- Manage the company's subscription within the permitted lifecycle.

## 5. Platform Administrator

- View/manage users.
- Approve or reject recruiter registrations after reviewing employment proof.
- Manage businesses and business status.
- Manage subscription plans and company subscriptions.
- View subscription history/status.
- Perform platform-level administration.

## 6. Authorization principles

Authorization is enforced by backend services, not only by the frontend:

```text
Authentication
      |
      v
Role authorization
      |
      v
Resource/company ownership
      |
      v
Subscription entitlement
      |
      v
Operation
```

Examples:
- A recruiter cannot access another company's applications.
- A candidate cannot access another candidate's CV or interviews.
- A pending/rejected recruiter cannot sign in.
- Anonymous users cannot submit an authenticated application.
- Users can modify only their own notifications.

# SmartRecruit — System Architecture

## 1. Architecture Overview

SmartRecruit is a distributed microservices platform built with **React/TypeScript** and **Spring Boot**.

The architecture uses:


| Component                           | Description                                                                                                          |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 7 Business Services                 | Core domain services organized around business capabilities.                                                         |
| Spring Cloud Gateway                | Central API entry point for path-based routing and JWT validation.                                                   |
| Kubernetes-Native Service Discovery | Kubernetes Services provide stable DNS names and load balancing between gateway and backend workloads.              |
| PostgreSQL (Database-per-Service)   | Each microservice owns its dedicated PostgreSQL database.                                                            |
| Apache Kafka                        | Asynchronous domain event streaming and inter-service communication.                                                 |
| OpenFeign / REST                    | Synchronous service-to-service communication.                                                                        |
| Redis                               | Selective caching layer for read-heavy and frequently accessed data.                                                 |
| MinIO                               | Object storage for CVs, employment-proof documents, and other files.                                                 |
| External Integrations               | AI providers, payment gateways, email services, webhooks. |


### Core principles

1. Each service owns its data.
2. PostgreSQL is the source of truth for transactional data.
3. Redis is a performance layer, never the primary database.
4. Services never access another service's database directly.
5. OpenFeign/REST is used when an immediate response is required.
6. Kafka is used for asynchronous domain events.
7. Authorization is enforced by the backend.
8. Private files are stored in MinIO and accessed through authorized backend operations.
9. CQRS is used primarily where read requirements differ significantly from transactional workloads.

---

## 2. Business Services


| #   | Service              | Responsibilities                                         | Storage            |
| --- | -------------------- | -------------------------------------------------------- | ------------------ |
| 1   | Identity Service     | Authentication, users, profiles, recruiter approval, JWT | PostgreSQL         |
| 2   | Recruitment Service  | Businesses, jobs, applications                           | PostgreSQL + Redis |
| 3   | Candidate/AI Service | CVs, CV versions, AI analysis and recommendations        | PostgreSQL + MinIO |
| 4   | Subscription Service | Plans, subscriptions, trials, billing history            | PostgreSQL + Redis |
| 5   | Interview Service    | Scheduling, rescheduling, cancellation, delay requests   | PostgreSQL         |
| 6   | Notification Service | Email, in-app, webhook notifications                     | PostgreSQL         |
| 7   | Analytics Service    | Analytics read models and PDF reports                    | PostgreSQL + Redis |


### Service boundaries

- **Identity** owns accounts, authentication, roles, profiles, and recruiter approval.
- **Recruitment** owns businesses, jobs, and applications.
- **Candidate/AI** owns CV metadata, CV versions, document references, and AI processing.
- **Subscription** owns plans, subscriptions, trials, entitlements, and billing state.
- **Interview** owns interview scheduling and meeting-link metadata.
- **Notification** consumes events and manages notification delivery.
- **Analytics** owns reporting-oriented read models.

## 5. Service Communication

SmartRecruit uses two communication styles.

### 5.1 Synchronous communication — REST + OpenFeign

Use OpenFeign when a service needs an immediate response.

```text
Recruitment Service
       │
       │ OpenFeign / REST
       ▼
Identity Service
```

A Feign client must call another service's API. It must never access that service's database.

Feign requests that act on behalf of a user propagate the bearer token; the receiving service validates it rather than trusting the caller or gateway alone.

Synchronous calls should use appropriate resilience controls:

- Connection timeout
- Read timeout
- Bounded retry
- Circuit breaker
- Bulkhead where required

Resilience4j supplies these fault-tolerance controls for synchronous service calls. Retries should be limited to safe transient failures.

### 5.2 Asynchronous communication — Kafka

Use Kafka when downstream processing can happen independently.

```text
Recruitment Service
       │
       │ JobCreated
       │ ApplicationSubmitted
       ▼
   Apache Kafka
       │
       ├──────────────► Notification Service
       │
       └──────────────► Analytics Service
```

Kafka is the internal event backbone. Consumers process events through normal Kafka consumer mechanisms; Kafka is not treated as a database.

## 9. Authentication and Authorization

Candidate registration activates the account.

Recruiter registration creates a pending account until administrator approval.

Spring Security provides stateless authentication with JWT bearer tokens. The Identity Service issues tokens carrying stable identity and role information; protected services validate the token and do not rely on an HTTP session.

Passwords are stored as BCrypt hashes, never as plaintext.

Authorization follows a layered model:

```text
JWT Authentication
        │
        ▼
Role Check
        │
        ▼
Resource / Company Ownership
        │
        ▼
Subscription Entitlement
        │
        ▼
Operation
```

Authentication and authorization state remain authoritative in Identity Service and PostgreSQL. Redis is not used as the authoritative security store.

### API security controls

- Spring Cloud Gateway is the public API entry point. It validates JWTs on protected routes and forwards the bearer token to backend services for their own validation and authorization.
- Public API traffic uses HTTPS/TLS at the deployment edge; internal service traffic must use the environment's approved transport protections.
- Every service validates request data server-side. Frontend validation improves usability but is not a security boundary.
- Spring Security protects authenticated endpoints. RBAC restricts operations by role, with resource and company ownership checks for object-level access.
- Registration and login are public; other routes are protected unless explicitly documented as public.

| Control | Responsibility |
| --- | --- |
| Authentication | Spring Security and stateless JWT bearer-token validation |
| Authorization | RBAC, resource/company ownership checks, and subscription entitlements |
| Password storage | BCrypt password hashing |
| API perimeter | API Gateway, HTTPS/TLS, server-side input validation, and endpoint protection |
| Service calls | OpenFeign with bearer-token propagation where acting for a user, downstream token validation, and Resilience4j fault tolerance |

## 16. Cache Invalidation

Authoritative updates are written to PostgreSQL first.

```text
Client
  │
  ▼
Service
  │
  ▼
PostgreSQL
  │
  ├──► Invalidate related Redis entries
  │
  └──► Publish domain event
             │
             ▼
           Kafka
```

Cache invalidation is performed after a successful database update.

Operations that require invalidation include:

- Job creation
- Job update
- Job publication
- Job closure
- Job deletion

The database remains authoritative if cache invalidation fails. A later cache miss can retrieve current data from PostgreSQL.

## 17. Redis vs Kafka

Redis and Kafka solve different problems.


| Technology | Responsibility                               |
| ---------- | -------------------------------------------- |
| PostgreSQL | Authoritative business data                  |
| Redis      | Low-latency cache and read acceleration      |
| Kafka      | Asynchronous communication and domain events |


Kafka handles:

- Event propagation
- Service decoupling
- Notification processing
- Analytics processing

Redis handles:

- Repeated read acceleration
- Database load reduction
- Temporary cached results
- Read-model acceleration

They are not interchangeable.

## 19. Resilience

Resilience is required for synchronous service calls and external integrations where failures are possible.


| Pattern              | Purpose                                         |
| -------------------- | ----------------------------------------------- |
| Timeout              | Prevent indefinite synchronous calls            |
| Bounded retry        | Handle transient failures                       |
| Circuit breaker      | Stop repeated calls to an unhealthy dependency  |
| Bulkhead             | Isolate expensive or external processing        |
| Kafka retry / DLQ    | Handle failed event processing                  |
| Idempotent consumers | Tolerate duplicate event delivery               |
| Transactional outbox | Coordinate database changes and outgoing events |


Retries must be limited to transient failures and safe/idempotent operations. Resource-creating `POST` operations must not be blindly retried unless idempotency is guaranteed.

Example:

```text
Service A
    │
    ▼
  Feign
    │
    ▼
Circuit Breaker
    │
    ▼
Timeout
    │
    ▼
Bounded Retry + Backoff
    │
    ▼
Service B
```

---

## 20. Transactional Outbox

Services that update their database and publish Kafka events should use the transactional outbox pattern when reliable event publication is required.

```text
                 Service
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   Business Data          Outbox Record
     PostgreSQL             PostgreSQL
          │                   │
          └─────────┬─────────┘
                    │
                    ▼
             Outbox Publisher
                    │
                    ▼
                 Kafka
```

The pattern prevents a successful database transaction from being committed while its corresponding Kafka event is lost.

## 26. Architecture Constraints

The following rules are architectural constraints:

- No direct cross-service database access.
- No frontend-only authorization.
- No public access to private CV files.
- No direct React-to-AI-provider integration.
- No secret credentials committed to Git.
- No auto-increment integer primary keys.
- No internal video-conferencing implementation; interviews store external meeting links.
- OpenFeign/REST is used for required synchronous service communication.
- Kafka is used for asynchronous domain events and event-driven notification/analytics processing.
- PostgreSQL remains the source of truth for transactional business data.
- Redis is only a cache/read-performance layer.
- Redis must not replace PostgreSQL as the authoritative data store.
- Redis should be introduced selectively rather than automatically added to every service.
- Cached data must use TTLs and/or explicit invalidation.
- Application status, interview state, and billing history remain authoritative in PostgreSQL.
- Analytics may use a dedicated CQRS read model because its read requirements differ from transactional workloads.
- Cache failures must not make business data unavailable; services must be able to fall back to PostgreSQL.

# SmartRecruit Contribution Guide

## 1. Repository organization


## 2. Ownership principle

Each service owns its domain logic, database and migrations. No developer may bypass a service API to read/write another service's database.

## 3. API and Swagger rules

Every service must:
- Expose OpenAPI documentation.
- Keep Swagger examples accurate.
- Keep Swagger UI and `/v3/api-docs` publicly accessible for the UI to load; require JWTs for protected API operations.
- Declare the shared HTTP Bearer JWT scheme in OpenAPI when the service has protected operations.
- Use `/api/v1`.
- Use UUID/GUID identifiers.
- Return consistent validation/error responses.
- Add integration/contract tests for important endpoints.

## 4. Service communication

Use **Spring Cloud OpenFeign** for synchronous service-to-service REST communication.

Use **Kafka** for asynchronous domain events.

Do not create direct database dependencies between services.

## 5. Resilience rules

Feign clients must define:
- Connect timeout.
- Read timeout.
- Bounded retries with backoff for transient/safe failures.
- Circuit breaker for important dependencies.

Do not retry non-idempotent commands blindly. Use idempotency keys or idempotent command handling when a command can be retried safely.

Kafka consumers must use bounded retries and dead-letter handling.

## 6. Kafka rules

Events should represent domain facts, for example:

```json
{
  "eventId": "uuid",
  "eventType": "ApplicationStatusChanged",
  "aggregateId": "uuid",
  "occurredAt": "...",
  "version": 1,
  "payload": {}
}
```

Do not put passwords, tokens, CV binary content or other sensitive secrets into Kafka events.

Notification Service consumes relevant events and transforms them into notification records and outbound delivery actions. It must not treat Kafka as a query database.

## 7. Database rules

- PostgreSQL per service.
- Every primary key is UUID/GUID.
- No `SERIAL`, `BIGSERIAL` or auto-increment integer PKs.
- Use Flyway migrations.
- No cross-service foreign keys.
- Store timestamps consistently.

## 8. File-storage rules

CVs and recruiter employment-proof files are stored in MinIO. PostgreSQL stores metadata/object keys. Do not commit uploaded files to Git.

## 9. Interview rules

The Interview Service stores an external meeting URL supplied by the recruiter. SmartRecruit does not implement video conferencing. URLs may point to Zoom, Google Meet or another approved provider.

## 10. Security rules

- Backend authorization is authoritative.
- Verify recruiter company/resource ownership.
- Candidates can access only their own private resources.
- Private CV objects require controlled access.
- Never commit secrets.

## 11. Testing

### Unit tests
Business logic, validation, authorization and resilience behavior.

### Integration tests
Spring context, PostgreSQL, MinIO and Kafka interactions where relevant.

### API/contract tests
Use OpenAPI/Swagger during development and automated API tests for stable contracts.

### Resilience tests
Simulate timeout, transient failure, circuit opening and recovery.

### Security tests
Verify role restrictions, ownership checks and recruiter approval rules.

## 12. Pull requests

A PR should describe:
- Business requirement/issue.
- Services affected.
- Database migrations.
- API changes.
- Kafka event changes.
- Resilience implications.
- Tests performed.

- UUID/GUID identifiers are used.

# SmartRecruit Database Architecture

## 1. Database strategy

SmartRecruit uses **PostgreSQL with database-per-service ownership**. Every service owns its data and exposes data only through its API/events. No service directly queries another service's database.

### Mandatory identifier rule

**Every database primary key is a GUID/UUID.** Auto-incremented `INT`, `BIGINT`, `SERIAL` and `BIGSERIAL` primary keys are not permitted.

Recommended PostgreSQL type:

```sql
id UUID PRIMARY KEY
```

UUIDs should be generated application-side or with PostgreSQL UUID support, consistently across all services.

## 2. Logical databases

| Service | PostgreSQL database | Main data |
|---|---|---|
| Identity | `smartrecruit_identity` | Users, candidate/recruiter/admin profiles, recruiter approval |
| Recruitment | `smartrecruit_recruitment` | Businesses, memberships, job offers, applications |
| Candidate/AI | `smartrecruit_candidate` | CV metadata, analysis, recommendations |
| Subscription | `smartrecruit_subscription` | Plans, subscriptions, history, invoices |

## 3. Identity Service: inheritance model

The domain model uses a base `users` table plus role-specific tables. This implements the requirement that **Candidate, Recruiter and Platform Administrator inherit common User properties while adding their own properties**.

```text
users
  |
  +---- candidate_profiles
  |
  +---- recruiter_profiles
  |
  +---- admin_profiles
```

All tables use GUID/UUID primary keys. The child primary key is also a foreign key to `users.id`. This is a joined-inheritance style model.

### `users`

Suggested fields:

```text
id UUID PK
email VARCHAR UNIQUE NOT NULL
password_hash VARCHAR NOT NULL
first_name VARCHAR NOT NULL
last_name VARCHAR NOT NULL
phone VARCHAR
address VARCHAR
city VARCHAR
state VARCHAR
country VARCHAR
postal_code VARCHAR
role VARCHAR NOT NULL
status VARCHAR NOT NULL
created_at TIMESTAMP
updated_at TIMESTAMP
```

### `candidate_profiles`

```text
user_id UUID PK/FK -> users.id
profile-specific fields
```

Examples include candidate career/profile information and candidate-specific preferences. CV files are not stored in this database.

### `recruiter_profiles`

```text

employment_proof_object_key VARCHAR
approval_status VARCHAR
approved_by UUID
approved_at TIMESTAMP
rejection_reason VARCHAR
```

The employment-proof binary is stored in MinIO; this table stores metadata/reference information.

### `admin_profiles`

```text
user_id UUID PK/FK -> users.id
admin-specific fields
```

Platform Administrator accounts are system/platform accounts but still inherit common User properties.

## 12. Migrations

Use Flyway per service. Every migration must respect the UUID primary-key rule. Example:

```sql
CREATE TABLE example (
    id UUID PRIMARY KEY,
    created_at TIMESTAMP NOT NULL
);
```

Migration ownership belongs to the service that owns the table.

## 13. Consistency and events

For reliable event publication, use a transactional outbox in services that both persist business state and publish Kafka events:

```text
Service DB transaction
       |
       +--> business data
       +--> outbox event
                |
                v
             Kafka
```

Consumers must be idempotent because events may be delivered more than once.

# SmartRecruit Production and Development Architecture

## 1. Purpose

This document defines how the seven-service SmartRecruit architecture is developed, packaged and deployed.

## 2. Development model

Developers use Docker Compose for shared local infrastructure and can run individual Spring Boot services locally for fast development. Each service has Swagger UI for REST API testing.

Recommended local infrastructure:

- PostgreSQL databases/service instances.
- Kafka.
- Kafka UI or equivalent development tooling.
- MinIO for S3-compatible CV/document storage.

The Identity Service requires `POSTGRES_PASSWORD`, `IDENTITY_JWT_SECRET` (at least 32 characters), `MINIO_ROOT_USER`, and `MINIO_ROOT_PASSWORD` in its environment. Configure `IDENTITY_DB_URL` when the service cannot use the local Compose default.

All services that accept Identity Service JWTs must be configured with the same `IDENTITY_JWT_SECRET` and issuer (`smartrecruit-identity`). Swagger UI and `/v3/api-docs` are publicly accessible for development and documentation loading; protected API operations continue to require a valid JWT.

For team consistency, Dockerfiles and Compose configuration are version-controlled. Container images can be published to a shared registry for integration testing.

## 3. Production topology

```text
                         React
                           |
                           v
                    API Gateway / Ingress
                           |
      +--------------------+--------------------+
      |         |          |         |           |
      v         v          v         v           v
 Identity  Recruitment Candidate Subscription Interview
      |         |          |         |           |
      +---------+----------+---------+-----------+
                           |
                         Kafka
                           |
                    +------+-------+
                    |              |
                    v              v
              Notification     Analytics

Candidate/AI Service ----> MinIO
All services ------------> PostgreSQL (database-per-service)
```

## 4. Kubernetes

Production runs on Kubernetes. Kubernetes Services provide native service discovery. There is no requirement for Eureka.

Typical components:

- Ingress/API Gateway.
- Kubernetes Deployment per service.
- Kubernetes Service per service.
- ConfigMaps for non-secret configuration.
- Secrets for credentials/tokens.
- Persistent storage for PostgreSQL/MinIO where self-hosted.
- Kafka deployment or managed Kafka.

Internal service URLs follow Kubernetes DNS, for example:

```text
http://identity-service
http://recruitment-service
http://candidate-ai-service
http://subscription-service
http://interview-service
http://notification-service
http://analytics-service
```

Feign clients target these service names through configuration.

## 5. File storage

MinIO is the selected S3-compatible storage technology for CVs and recruiter employment-proof documents. PostgreSQL stores metadata and object keys.

```text
Candidate/Identity upload
          |
          v
       MinIO
          ^
          |
PostgreSQL stores metadata/object key
```

Private objects must not be anonymously readable. Access should be mediated by the owning service and, where appropriate, short-lived signed URLs.

## 6. Kafka

Kafka is the internal event backbone. Example events include:

```text
JobCreated
JobClosed
JobDeleted
ApplicationSubmitted
ApplicationStatusChanged
InterviewScheduled
InterviewCancelled
InterviewDelayRequested
SubscriptionActivated
CVUploaded
ATSAnalysisCompleted
```

The Notification Service uses consumer groups to process relevant events. It then creates in-app notifications and can trigger email or webhooks.

## 7. Resilience

All important synchronous Feign integrations must use bounded resilience configuration:

- Connect timeout.
- Read timeout.
- Bounded retry count.
- Exponential/backoff delay.
- Circuit breaker.
- Optional bulkhead for expensive AI/external work.

Example flow:

```text
Feign Client
    |
    v
Timeout
    |
Retry (bounded)
    |
Circuit Breaker
    |
    v
Downstream Service
```

Kafka consumers use retry and dead-letter topics. Consumers are idempotent.

## 8. Security

- HTTPS at the public edge.
- JWT authentication.
- Role and resource ownership authorization.
- Recruiter company isolation.
- Private CV/document access.
- Secrets stored outside Git.
- No direct browser access to internal service databases.

## 9. Observability

Use Spring Boot Actuator and Micrometer for:

- Health endpoints.
- Metrics.
- Request timing.
- Feign dependency timing/failures.
- Kafka consumer metrics.
- Structured logs.
- Distributed tracing foundations.

## 10. Scaling

Services scale independently. Public job browsing can cause higher load on Recruitment Service, while AI processing can require separate scaling for Candidate/AI workers. Notification and Analytics consumers can scale horizontally using Kafka consumer groups.

## 11. Database identifiers

Every PostgreSQL primary key is UUID/GUID. Auto-increment integer identifiers are prohibited. Cross-service IDs are logical references, not cross-database foreign keys.
